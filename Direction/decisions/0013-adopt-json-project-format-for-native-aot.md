# 0013. Adopt JSON as an AOT-safe project file format, phased in alongside XML

- **Status:** Accepted
- **Date:** 2026-07-31
- **Deciders:** Victor Chelaru, Claude

## Context

A user reported a Native AOT + trimmed publish crash: `GumProjectSave.Load` throws `NotSupportedException: MakeGenericMethod() is not compatible with AOT compilation` from inside `System.Xml.Serialization.XmlSerializer`'s reflection-based reader. Root cause: `FileManager.GetXmlSerializer` (`ToolsUtilities/FileManager.cs:905-926`) calls `new XmlSerializer(type)` (Release) / `XmlSerializer.FromTypes` (Debug) — both rely on runtime reflection/codegen, which Native AOT forbids. `GumFileSerializer.GetCompactSerializer` is worse: it builds its serializer from `XmlAttributeOverrides` at runtime, and `XmlSerializer(Type, XmlAttributeOverrides)` never uses a pregenerated serializer even when one exists via `sgen`/`Microsoft.XmlSerializer.Generator` — it always falls back to the dynamic path. So making the existing `XmlSerializer`-based path AOT-safe via pregeneration is a dead end without first redesigning the compact format away from runtime overrides.

Prior AOT work (#4105/#4106) fixed a different, narrower bug (unguarded reflection scanning in `RegisterRuntimeTypesThroughReflection`) and added `Tests/NativeAotSmoke.Harness` as regression coverage — but that harness only calls `GumService.Default.Initialize` with default in-memory visuals, never loading a real project file, so it never exercised this code path. This gap shipped invisibly.

The real fix is not "make XML work under AOT" vs "switch to JSON" — reflection is the actual blocker, and a hand-rolled AOT-safe XML reader would work in principle. But hand-rolling means every future Save-class property change needs matching hand-written parse/write code forever, with no compiler safety net — worse long-run cost than a one-time migration. `System.Text.Json` with a source-generated `JsonSerializerContext` is .NET's actual supported AOT serialization path: compile-time generated, no runtime reflection, and it comes with real side benefits — smaller and faster than the current XML shape, and easier for other tooling/environments to consume (Gum already ships Python typings under `Runtimes/Python/gumui`).

Gum already has precedent for two on-disk shapes under one extension (legacy element-based vs compact attribute-based XML, detected via `IsGumxCompactFormat`), so introducing a second serialization format is not structurally novel — the loader already has a content-detection seam, though this decision does not reuse it (see Alternatives).

File family affected, all routed through the same `FileManager.GetXmlSerializer`/`GumFileSerializer`/`XmlDeserializeFromStream` machinery: `.gumx` (`GumProjectSave`), `.gusx` (`ScreenSave`), `.gucx` (`ComponentSave`), `.gutx` (`StandardElementSave`), `.behx` (`BehaviorSave`), `.ganx` (`ElementAnimationsSave`, the `{ElementName}Animations.ganx` sidecar loaded by `GumService.LoadAnimations`).

## Decision

We will add JSON as a new, additional Gum save format using `System.Text.Json` with a source-generated `JsonSerializerContext`, rather than attempting to make the existing `XmlSerializer`-based path AOT-safe or hand-rolling a replacement XML reader.

- JSON files use distinct new extensions per current family — `.gumj`/`.gusj`/`.gucj`/`.gutj`/`.behj`/`.ganj` — so file identity is unambiguous to users, OS file associations, and external scripts. No content-sniffing between XML and JSON.
- New projects created by the tool default to JSON. Existing XML projects are unaffected until a user explicitly converts them (a "Convert Project to JSON" tool action / `gum-cli` command) — Gum never silently rewrites a user's on-disk format.
- XML read+write support is retained indefinitely; this ADR does not set a retirement date. That is a separate future decision, made once JSON has real-world mileage.
- Round-trip fidelity is validated against real project fixtures before anything ships user-facing: every `.gumx`/`.gucx`/etc. file already checked into this repo, plus an external maintainer-provided production project, all round-tripped losslessly (verified against an independent XML-oracle diff, not just JSON self-consistency).
- **Phase 1 converts the whole reachable file family together, not `GumProjectSave` alone.** `GumProjectSave.Load` → `PopulateElementSavesFromReferences` (`GumProjectSave.cs:629-716`) eagerly deserializes every referenced `ScreenSave`, `ComponentSave`, `StandardElementSave`, and `BehaviorSave` via the same XML path, immediately after the project file itself loads. A `.gumj` project that still references XML `.gusx`/`.gucx`/`.gutx`/`.behx` files hits the identical AOT crash one line later — it doesn't fix anything, it just moves the crash. `ElementAnimationsSave`/`.ganx` belongs in the same set for a related reason, not eager-loading: `GumService.LoadAnimations`/`LoadAnimationsFromProvider` (`MonoGameGum/GumService.cs:779-837`) deserializes every `*Animations.ganx` via the exact same unsafe path, so any real game that uses animations hits the identical crash. So phase 1 is all six types together: `GumProjectSave`/`.gumx`, `ScreenSave`/`.gusx`, `ComponentSave`/`.gucx`, `StandardElementSave`/`.gutx`, `BehaviorSave`/`.behx`, `ElementAnimationsSave`/`.ganx`.

## Consequences

- Fixes the Native AOT crash via .NET's actual recommended path (source-gen), not a workaround.
- Every behavior-preserving XML quirk needed an explicit, deliberate JSON-side equivalent — nothing was free just by switching serializers. Known examples: `SetsValue` default suppression for behaviors (`GumFileSerializer.AddVariableSaveOverrides`), the "append to existing list rather than replace" read semantics noted in `GumProjectSave.cs:223-226`, and the attribute-vs-element choices made for git-diff-friendliness in the compact format. The legacy `LocalizationFile`/`LocalizationFilesArray` XML back-compat shim has no JSON equivalent — it exists purely to keep old XML readers working, and JSON has no old readers to be compatible with.
- Two formats must be maintained side by side for an unbounded period, meaning double the format-specific test surface for as long as that lasts.
- New file extensions mean docs, `gum-cli`, samples, and any external tooling that recognizes `.gumx`/etc. eventually need JSON-extension awareness too.
- Does not, by itself, help users who never convert — XML stays exposed to the same AOT crash until they do. Native AOT + trimmed + XML project files remains a documented unsupported combination until conversion.
- `Tests/NativeAotSmoke.Harness` should eventually load a real (converted) project file under `PublishAot=true`, closing the exact coverage gap that let the original bug ship unnoticed.
- The JSON DTOs are internal-only, never exposed as public API — only `GumJsonFileSerializer`/`GumAnimationJsonFileSerializer` are public, and they accept/return the real standard Save types, not shadow ones. `System.Text.Json`'s `JsonStringEnumConverter` and `[JsonDerivedType]` were both avoided (the former is reflection-based pre-.NET-8 and not AOT-safe generically; the latter is .NET 7+ only and would break the net6.0 FRB1 target) — enums serialize as plain ints, and closed-generic polymorphism (`VariableListSave<T>`) is modeled as one DTO with a typed nullable property per element type.

## Alternatives considered

- **Hand-roll an AOT-safe XML reader/writer, keep existing extensions and wire format.** Rejected as the primary path — no format migration needed, but every future Save-class property change requires hand-maintained parse/write code indefinitely, with no compiler safety net.
- **Pregenerate `XmlSerializer` via `sgen`/`Microsoft.XmlSerializer.Generator`.** Rejected — the compact format's `XmlAttributeOverrides` constructor never uses a pregenerated serializer regardless, so this doesn't fix the crash without first redesigning the compact format away from runtime overrides.
- **Auto-upgrade existing projects to JSON transparently on next save.** Rejected — a full XML→JSON rewrite is a much larger unexpected diff than the existing `Version` auto-stamp behavior, especially for git-tracked projects. Explicit opt-in keeps the user in control.
- **Reuse existing extensions with content-sniffing** (mirroring `IsGumxCompactFormat`). Rejected — unlike legacy/compact XML (both XML, same external tooling expectations), XML vs JSON are genuinely different formats; external editors, git diff/merge tooling, and file-association-based workflows benefit from the format being unambiguous from the filename alone.
- **Gate JSON auto-save behind a project schema-version bump** (e.g. "opening a v4 project always saves it as JSON"). Rejected — `Version`/`GumxVersions` already has an established, orthogonal meaning (gating which variables/features are available, e.g. the v3 shape-variable expansion), not file format. Overloading it conflates two independent decisions a user might want to make separately, and "any incidental save silently rewrites the format" reintroduces the same silent-flip risk as the rejected auto-upgrade alternative above.
